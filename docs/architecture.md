# Платформа для портирования PS4-игр на macOS: архитектура

Автор: Iuliia Gailova. Черновик 1, 20.11.2026. Основа — RnCPort (Ratchet & Clank) и SpartanPort (God of War III).

## 1. Цель

Не ускорить одну игру, а сделать **систему**, в которой каждая следующая PS4-игра портируется дешевле предыдущей:
- **общее ядро** (рантайм PS4, графика, мост, инструменты) улучшается один раз для всех игр;
- **игра** = свой дамп + **профиль** (патчи, настройки, известные проблемы, тестовые сценарии) + недостающие системные функции, которые сразу попадают в общий рантайм;
- максимальная скорость на Apple Silicon, а M1 с 8 ГБ — эталонная тестовая машина: на ней видны все проблемы производительности.

## 2. Что есть сейчас (ноябрь 2026)

Один x86-64-процесс под Rosetta 2:

| часть | язык | где | что делает |
|---|---|---|---|
| загрузчик и рантайм (`src/runtime*.c`, `probe.c`) | C | x86 | ELF игры, линковка импортов (NID), память PS4 (общий объект `shm_open`), потоки, синхронизация, файлы, сохранения, звук (Ajm, ATRAC9), геймпад (SDL), сервисы PSN-заглушки |
| графическая библиотека (`gpu/`, `libspartanportgpu.dylib`) | C++20 | x86 | видеоядро shadPS4 (разбор PM4, перевод шейдеров, кеши буферов и текстур, Vulkan), окно SDL, оверлей; HLE-библиотеки GnmDriver, VideoOut, event queue ядра, AvPlayer |
| KosmicKrisp (Mesa) | C/ObjC | x86 | Vulkan → Metal |
| `run.py`, `scripts/` | Python | — | запуск, патчи, настройки, резервные копии сохранений |

Граница рантайм ↔ графика сейчас — вызовы функций в одном процессе: `spartanportgpu_init`, `spartanportgpu_resolve` (HLE-функции графики по NID), `runtime_memory_set_gpu_hooks` (map/unmap/invalidate), `spartanportgpu_handle_fault` (сбои страниц), плюс десяток функций настроек и ввода.

### Что показали замеры R&C на M1 8 ГБ (драка, 3 с трассы)

- Игра каждый кадр синхронизируется с GPU в нескольких местах (метки EOP, считывание картинок, запись в буферы, которые пишет GPU). Поток рендера игры ~58% времени крутится в ожидании.
- GPU занят ~1/3 времени. Остальное — задержка нашей цепочки на процессоре: поток команд → конвейер отрисовки → поток записи Vulkan → KosmicKrisp. Всё это под Rosetta, с передачами между потоками.
- Устранение отдельных ожиданий почти не меняет FPS: время перетекает в следующее. Рычаги — сокращение задержки **всей** цепочки (нативный процесс) и времени GPU (KosmicKrisp).

### Долг: игро-специфичное внутри ядра

- `run.py`: ветки по `CUSA01047` (режимы считывания, частота отправки), папка игры по умолчанию.
- `scripts/patches.py`: таблица игр зашита в код (`GAMES = [...]`).
- рантайм: хуки God of War (`orb_hook.h`, `qte_hook.h`, `actor_hook.h`, `damage_hook.h`, `menu_hook.h`, `cheat_hook.h`) подключены в `probe.c`;
- графика: временной апскейлер и «motion» привязаны к сцене God of War III; оверлей с настройками GoW.

## 3. Целевая архитектура

```text
┌──────────────── x86-64 процесс (Rosetta 2) ────────────────┐   ┌──────────── arm64 процесс (нативный) ────────────┐
│ код игры (eboot, модули)                                    │   │ графический сервис                                │
│ рантайм PS4 (C): память, потоки, файлы, звук, сохранения    │   │  видеоядро shadPS4 (C++): PM4, шейдеры, кеши      │
│ HLE-фасады графики: GnmDriver, VideoOut, equeue (тонкие)    │   │  KosmicKrisp → Metal                              │
│ обработчик сбоев страниц → запрос в мост                    │   │  окно, ввод (SDL), оверлей                        │
└──────────────┬──────────────────────────────────────────────┘   └──────────────┬────────────────────────────────────┘
               │                     МОСТ (общая память)                          │
               ├── память игры: тот же объект shm, отображён по тем же адресам ──┤
               ├── кольцо отправок: буферы команд (адреса в памяти игры) ────────►│
               ├── кольцо событий: EOP/flip/прерывания ◄─────────────────────────┤
               ├── запросы защиты страниц ◄──── / сбои записи ────► ────────────┤
               └── состояние ввода, окна, настроек (общая структура) ◄───────────┘
```

### 3.1 Почему так

- Код игры исполняется только в x86-процессе: Rosetta — единственный способ его запустить. Значит, рантайм остаётся x86 (C, как сейчас).
- Графика не исполняет код игры, она читает его данные. Её можно вынести в нативный процесс и убрать Rosetta с самой длинной цепочки.
- Память игры уже лежит в общем объекте (`shm_open`). Второй процесс отображает его по **тем же виртуальным адресам**, поэтому адреса в командах GPU действительны без перевода. Проверено 20.11.2026: `MAP_FIXED` по `0x800000000`, `0x7000000000`, `0x8000000000`, `0x867c000000`, `0xfc00000000` работает и в arm64-, и в x86-процессе; `0x1000000000` (зарезервированная macOS область) недоступна в обоих — так же, как под Rosetta, что уже учтено патчами адресного пространства.
- Метки (fences) GPU-процесс пишет прямо в общую память — игра, крутящаяся на метке, видит их без IPC.

### 3.5 Граница сегодня (замер 20.11.2026)

- **GnmDriver:** 114 функций, к GPU обращаются 8 (`SubmitCommandBuffers[ForWorkload]`, `SubmitAndFlip…`, `SubmitDone`, `DingDong[ForWorkload]`, `Map/UnmapComputeQueue`); остальные ~106 собирают пакеты PM4 в памяти игры и остаются в x86.
- **VideoOut:** 17 функций работают с состоянием порта (буферы, статус флипа, vblank) — его можно держать в x86; в графику уходит «покажи буфер» (`Presenter::PrepareFrame/Present`) и обратно «показан».
- **equeue** (события ядра) — рантайм; из графики приходят только прерывания (EOP, flip, GPU idle).
- **AvPlayer** — работа процессора, остаётся в x86.
- **Графика → рантайм:** `runtime_memory_{region,clamp,is_mapped,write_backing,gpu_protect,set_gpu_hooks}`, время (`read_tsc`, `process_time_*`), `thread_attach_host`, `file_translate`, ошибки.
- **Рантайм → графика:** `spartanportgpu_init/register_kernel/resolve`, `handle_fault`, `main_loop` (окно SDL), ~12 функций интерфейса (выбор, ввод текста, мышь, вибрация, кадры видео).

### 3.2 Мост: протокол

| канал | направление | содержимое | механизм |
|---|---|---|---|
| память игры | обе | весь пул PS4 | общий `shm`, одинаковые адреса |
| отправки | x86 → arm64 | `{очередь, адреса и размеры DCB/CCB, флаги flip}` | кольцо SPSC в общей памяти + пробуждение `os_sync_wake_by_address_any` (общая память) |
| события | arm64 → x86 | EOP/EOS-прерывания, flip, «GPU idle» | кольцо + пробуждение; equeue в x86 доставляет их игре |
| карта памяти | x86 → arm64 | map/unmap/protect диапазонов (сейчас `runtime_memory_set_gpu_hooks`) | кольцо, упорядоченное с отправками |
| защита страниц | arm64 → x86 | «защитить/снять защиту с диапазона» (отслеживание записей CPU) | кольцо; x86 выполняет `mprotect` у себя |
| сбой записи | x86 → arm64 → x86 | «игра пишет в адрес X» → «готово, можно писать» | запрос/ответ; самая чувствительная к задержке часть |
| ввод, окно | arm64 → x86 | состояние геймпада/клавиатуры, фокус, размер | общая структура с версией (seqlock) |
| настройки, оверлей | обе | меню, переключатели | общая структура |

Ожидания между процессами: `os_sync_wait_on_address` / `os_sync_wake_by_address_*` с флагом общей памяти (macOS 14.4+; нам нужен macOS 26 и так), без системных вызовов в быстром пути (сначала короткое ожидание на атомике).

### 3.3 Отслеживание записей CPU — главный риск

Сейчас слой GPU сам ставит защиту страниц и ловит сбои в своём процессе. После разделения:
1. GPU-процесс решает, какие страницы отслеживать, и шлёт команды защиты в x86.
2. x86 ловит сбой, отправляет «запись в X» и ждёт ответа (GPU-процесс скачивает свежие данные GPU в память, обновляет учёт).
3. Задержка запроса/ответа на M1 — десятки микросекунд; сбоев в кадре R&C — десятки. Приемлемо, но протокол должен пакетировать и избегать лишних сбоев (окна, как сейчас `SPARTAN_FAULT_WINDOW`).

Альтернатива на потом: часть учёта (битовая карта «страница грязная») в общей памяти, чтобы x86 решал простые случаи без запроса.

### 3.4 Языки

- x86-рантайм — **C** (как сейчас).
- графический сервис — **C++20** (видеоядро shadPS4), KosmicKrisp — C/Objective-C, нативная сборка arm64.
- мост — заголовок на **C** (общие структуры, кольца, атомики), используемый обеими сторонами.
- инструменты — Python (запуск, патчи, автотесты, разбор трасс).

## 4. Профиль игры

Файл данных на игру, без кода. Предлагаемый формат — TOML (читается и человеком, и Python, и C++).

```toml
# games/CUSA01047/profile.toml
title = "Ratchet & Clank"
title_ids = ["CUSA01047"]            # регионы: CUSA01073, CUSA01928 — по мере проверки
[[builds]]
version = "01.00"
eboot_sha256 = "52b76606…"
patches = "patches/CUSA01047.xml"    # обязательные патчи (адресное пространство) и по желанию
[gpu]
readback = "stale"                   # precise | deferred | stale
flush_draws = 100
[memory]
staging_low_ram = true
[known_issues]
fire_green_bars = "редкие зелёные полосы на фоне огня, 0.5 с (stale?)"
[test]
menu = ["42 hold cross", "42.3 release", "48 hold cross", "48.3 release"]   # титул → «Продолжить»
replays = ["replays/fight1b.pad"]
```

Ядро читает профиль по Title ID из `param.sfo`; переменные окружения по-прежнему переопределяют всё (для экспериментов). Игро-специфичные модули (хуки модов GoW, апскейлер GoW) включаются профилем и живут в `games/<id>/` или в отдельных модулях ядра с явным флагом.

## 5. Репозитории

Предложение (решение за вами, см. §8):

```text
ps4mac_port/                ← ядро (вырос из SpartanPort, GPL-2.0)
  runtime/   (C, x86)       ← сейчас src/

  bridge/    (C-заголовки)
  tools/     (Python: launcher, patches, autotest, trace)
  games/

```

## 6. План миграции

Каждый шаг заканчивается рабочей игрой (R&C и GoW III) и замером на автотесте.

1. **Профили и чистка ядра** (2–3 дня): новый репозиторий `ps4mac_port` из текущего RnCPort; `CUSA01047` и таблица `GAMES` — из кода в `games/*/profile.toml`; патч GoW III убран (игра остаётся в SpartanPort). Ничего не меняется в скорости. **Сделано 20.11.2026** (коммит «Platform: game profiles»). Хуки модов GoW (рантайм `probe.c`, оверлей, `spartanport_actors/orbs`, настройки, ~10 тестов) вырезаются вместе с переделкой оверлея в универсальный: это одна и та же часть кода; до тех пор они безвредны — ставятся только при совпадении сигнатур кода GoW.
2. **Интерфейс моста внутри процесса** (3–5 дней): заменить прямые вызовы рантайм ↔ графика на очереди из §3.2, всё ещё в одном процессе. Проверяем, что игры работают через протокол.
   - **Сделано 20.11.2026:** граница описана (§3.5); `bridge/ps4mac_bridge.h` — формат сообщений и кольца; `gpu/shim/ps4mac_graphics.{h,cpp}` — фасад `Ps4mac::Gfx`, через который GnmDriver отправляет работу (SubmitGfx/Compute/Done, IsIdle, вычислительные очереди). В одном процессе фасад вызывает ядро GPU напрямую; R&C — те же 10,7 FPS. VideoOut тоже идёт через фасад (регистрация буферов, подготовка и показ кадра, HDR, гамма, флипы с CPU через поток команд GPU) — те же 10,7 FPS. Карта памяти, сбои и защита страниц уже были узкими C-швами (обратные вызовы `runtime_memory_set_gpu_hooks`, `spartanportgpu_handle_fault`, `runtime_memory_gpu_protect`) — они записаны в `bridge/ps4mac_bridge.h` как каналы моста. **Шаг 2 завершён**; проверка протокола через настоящие очереди переносится в шаг 3.
3. **Второй процесс** (1–2 недели): лаунчер запускает arm64-сервис, передаёт ему `shm`, сервис отображает память по тем же адресам; отправки, события, карта памяти, защита страниц и сбои — через мост. Окно и ввод — в сервисе.
4. **Сборка arm64**: KosmicKrisp и зависимости нативно; `build-deps.sh` собирает обе архитектуры.
5. **Замеры и настройка**: трасса, EOP-тайминг, драка R&C до/после; затем GPU-сторона KosmicKrisp (барьеры, разрывы проходов).
6. **Отложено — апскейлинг FSR для R&C** (проверить позже, 24.11.2026). Код временного апскейлера (FSR 3.1 / FSR 4, `vk_temporal_upscaler`, библиотека `gpu/third_party/fsr-vulkan`) достался от SpartanPort и привязан к кадру God of War III: ждёт его шейдер сведения `9a9cf8a9`, которого в R&C нет; FSR 1 выключен в коде. Для R&C апскейлер и отслеживание камеры выключены (`run.py`: `SPARTAN_UPSCALER=none`, пока не включён экспериментальный переключатель лаунчера) и ничего не стоят. Возможная выгода: R&C упирается в GPU — рисовать сцену в 540p и восстанавливать FSR 3 до 1080p может дать больше FPS, чем нынешние 720p, при сопоставимой картинке. Разведка (~полдня): найти в R&C цвет сцены до постобработки, глубину, векторы движения и проход, где игра растягивает 720p до 1080p; замерить один проход FSR 3 на M1. Брать, только если FPS выше, чем без него.
7. **Вторая игра: God of War III Remastered (24.11.2026).** Дамп CUSA01623 v01.00 (внешний диск) без профиля и без патчей доходит до геймплея (меню, заставки 60 FPS, бой 13–15 FPS в 1080p); в ядре понадобилась одна правка (`run.py`: иконка окна из дампа, если её нет в профиле). Профиль `games/CUSA01623` — только патчи SpartanPort (пропуск заставок по X, чёрный экран при старте, порча текстур, разрешение; помечены 01.02, находят места по сигнатурам). Автотест `~/0_Games/GoWIII/autotest/bench.sh`: Новая игра → God (Normal) → заставки пропущены → первый бой на Гее, среднее FPS после 150 с (Кратос может погибнуть — экран смерти завышает среднее). Бой: 1080p 13,6 / 13,7 FPS; с настройками скорости R&C 14,7 / 15,0; с ними и патчем 720p 24,3 / 24,4; кадры верные. **Вывод — граница ядро/профиль:** настройки скорости R&C (отправка каждые 30 отрисовок, буферы в памяти игры, синхронизация по барьерам игры, без проверок границ буферов у драйвера, бюджет текстур 3,5 ГБ на Mac с 8 ГБ) перенесены в умолчания ядра (`run.py`); проверено после переноса: R&C бой 20,6 / 25,8, GoW III бой ~15. В профиле игры остаётся только своё: патчи (разрешение — главный рычаг FPS, ищется для каждой игры) и исключения (R&C: `SPARTAN_HOST_BUFFERS_SKIP`).
8. **Имя и данные игры — из дампа (24.11.2026).** Поле `app_name` в профилях убрано. Название окна, строки меню, Dock и игрового меню — `TITLE` из `param.sfo` («Ratchet & Clank™», «God of War® III Remastered»); сервис графики запускается через жёсткую ссылку с этим именем рядом с собой (`runtime_bridge.c`: macOS показывает в строке меню имя файла неупакованной программы). Данные (сохранения, настройки, кэш) — `~/Library/Application Support/ps4mac_port/<Title ID>`; прежняя папка `RnCPort` один раз переносится туда (`run.py`, `LEGACY_DATA_DIRS`). Иконка — своя из профиля или `sce_sys/icon0.png` дампа.

## 6.1 Шаг 3 подробно: второй процесс

Исходное состояние: один x86-процесс; главный поток держит окно SDL (Cocoa требует главного потока), игра идёт в отдельном потоке; геймпад и звук рантайм берёт через SDL в x86; все зависимости собраны только под x86.

Каждый подшаг заканчивается проверкой; после 3.0 — решение «идём дальше или меняем протокол».

| подшаг | что | проверка | срок |
|---|---|---|---|
| **3.0 Замер моста** | Микротест: x86-процесс (Rosetta) и arm64-процесс, общая память, кольцо SPSC, ожидание `os_sync_wait_on_address`. Меряем задержку «запрос → ответ» (как у сбоя записи) и пропускную способность сообщений. | Задержка туда-обратно; цель — ≤ 20–30 мкс. Если хуже — сразу закладываем пакетирование и битовую карту «грязных» страниц в общей памяти. | 1 день |
| **3.1 Сборка arm64** | `build-deps.sh` собирает вторую копию зависимостей под arm64 (Vulkan loader, KosmicKrisp с нашими патчами, SDL3, fmt, xxhash; FFmpeg и Zydis сервису не нужны). CMake: цель сервиса под arm64. | Пустой arm64-сервис открывает окно и создаёт устройство Vulkan на KosmicKrisp. | 1–2 дня |
| **3.2 Каркас сервиса** | Рантайм при старте запускает сервис (`posix_spawn`), передаёт ему дескриптор памяти игры (Unix-сокет, `SCM_RIGHTS`) и общий блок моста. Сервис отображает память по тем же адресам (заранее резервирует область), заводит кольца. Окно и главный цикл переезжают в сервис; x86-процесс остаётся без окна. | Сервис видит те же байты по тем же адресам (контрольные суммы с обеих сторон); закрытие окна завершает оба процесса; падение одного — понятная ошибка в другом. | 1–2 дня |

**3.2, находка (20.11.2026): адресное пространство arm64-процесса устроено иначе, чем под Rosetta.**

| диапазон | x86 под Rosetta (рантайм) | arm64 (сервис) |
|---|---|---|
| `0x3_0400_0000…0xF_C000_0000` | свободно: здесь «низкая» память — образ игры с `0x8_0000_0000`, куча рантайма с `0xE_0000_0000` | **общие системные библиотеки (dyld shared cache)** — занято |
| `0xF_C000_0000…0x70_0000_0000` | зарезервировано macOS | зарезервировано macOS |
| `0x70_0000_0000…0x80_0000_0000` | пространство PS4 (рантайм размещает здесь свои отображения) | **области malloc**, случайно при каждом запуске (100 запусков: не выше `0x7F_FA00_0000`; `MallocNanoZone=0`, `MallocXzoneEnabled=0` не помогают) |
| `0x80_0000_0000…0xFC_0000_0000` | пространство PS4 (слоты распределителя R&C после патча) | **свободно** — сервис может занять его первым делом |

Следствие: «те же адреса» возможны только в `0x80…0xFC_0000_0000`. Образ игры и отображения, адрес которых выбирает рантайм, должны жить там же (в режиме сервиса), а распределитель игры — не занимать эту часть (параметр профиля: у R&C число слотов 248 → например 232 освобождает верхние 32 ГБ `0xF4_0000_0000…0xFC_0000_0000`). Альтернатива — перевод адресов в видеоядре (сервис отображает память игры со сдвигом), но это правка каждого обращения к памяти игры в shadPS4. **Решение — вариант A, сделано 20.11.2026.** В режиме сервиса (`PS4MAC_SERVICE`) раскладка рантайма: слоты распределителя игры `0x80…0xE4_0000_0000` (R&C: патч профиля, 200 слотов вместо 248), отображения, адрес которых выбирает рантайм, — `0xE4…0xF4`, «низкая» память (образ игры, заглушки, выделения рантайма) — `0xF4…0xFC_0000_0000` в общем объекте. Сервис первым делом резервирует всё окно `0x80…0xFC`, «низкую» память отображает целиком, отображения пула — по сообщениям моста. Код игры и заглушек нельзя исполнять из общей памяти: перед `mprotect(PROT_EXEC)` такие страницы заменяются частной копией (сервису нужны данные, не код). Проверка: R&C до уровня, `PS4MAC_BRIDGE_CHECK=1` — **все 90 сверок контрольных сумм (прямая память и образ игры) совпали**; сервис завершается вместе с игрой; без сверки режим сервиса — те же 10,6–10,7 FPS, что и обычный. Обычный режим не изменился (200 слотов R&C хватает). **Изменено 23.11.2026: образ ниже куч, как на PS4.** «Низкая» память (образ, стеки, заглушки) — `0x80…0x88`, память игры (слоты распределителя R&C, 200 штук) — `0x88…0xEC`, отображения рантайма — `0xEC…0xFC`. Игры полагаются на этот порядок: пулы R&C отбрасывают объект по умолчанию из `.bss` образа только потому, что `указатель − база пула < 0`; при образе на `0xF4` перелёт на Керван падал (см. ниже). Первый уровень 25,8 FPS (было 25,7), бой 26,2 / 23,4 (23,5 / 26,4), Керван 2/2 без патча игры.

**Результат 3.4 (20.11.2026): отслеживание записей через мост — картинка верная.**

Сервис разбирает сбои по порядку — так же, как обработчик в `page_manager.cpp` (`OnWriteFault`, `ReadMemory`) — и кладёт результат в `fault_result[номер % 256]`. - **Проверка (R&C, M1 8 ГБ, режим сервиса):**

- Проверено и отброшено (21.11.2026): ожидание чтений при получении буфера только там, где оно нужно, и скачивание при сбое только нужных байтов окна. Ожидание `buffer-obtain` исчезает, но в пересчёте на 5 с ничего не меняется. Почти все долгие скачивания — одни и те же 16 байт (`0x81050bf940`): GPU пишет их каждый кадр, игра перезаписывает 8 из них через 3–4 отправки, ожидание 18–34 мс. Без скачивания (`SPARTAN_WRITE_NO_DOWNLOAD=1`) то же время уходит в чтения образов (1816 мс на 5 с), FPS и рывки те же.
- Вывод: ожидания — симптом, а не причина. Игра упирается в GPU, и кто-то в цепочке CPU ↔ GPU всё равно ждёт его. Рывки — это отдельные задания GPU, которые иногда идут в разы дольше обычного (EOP: обычно 20–25 мс, пики 50–680 мс без компиляций). Дальше искать, что в эти моменты делает сам GPU: проходы по подписям (`SPARTAN_GPU_PROFILE=labels`), давление памяти GPU на 8 ГБ.
- **Найдено (21.11.2026, трасса боя с подписями, `tools/gpu_trace/gpu_spikes.py`).** В рывках GPU не перегружен, а простаивает: провалы 86 и 299 мс совпадают с паузами, когда сервис ничего не отправляет в Metal (126 и 365 мс). Компиляции Metal в трассе нет. Каждый большой рывок идёт сразу за выделением нового промежуточного буфера: 160 МБ → 200 мс, 128 МБ → 150 мс, 896 МБ → 667 мс.

- **Сторона игры (Time Profiler на x86-процессе, `tools/profile/guest_profile.py`).** Главный поток игры занят процессором ~85% времени боя, большинство окон по 100 мс — на 100%: в бою игра упирается в свой главный поток, а не в GPU. Он исполняет код из области «Rosetta JIT»: код игры мы загружаем сами, поэтому Rosetta переводит его на лету, а не заранее (AOT, как обычные программы). Кэш перевода — 128 МБ адресов, ~35 МБ живых, из них 28 МБ выгружены в своп/сжатие (8 ГБ): обращение к ним ждёт возврата страниц.
- Отсюда направления по рывкам: меньше давления на память (наши копии памяти GPU, промежуточные буферы), меньше работы рантайма в главном потоке; проверить, даст ли что-то перевод заранее (код игры в виде Mach-O, который Rosetta переводит AOT).
- **Память сервиса в бою (21.11.2026, отчёт `Service memory`).** Сервис 5.4 ГБ, игра 1.5 ГБ, своп до 2 ГБ: образы ~0.9 ГБ, копии памяти игры для GPU ~1.2 ГБ, кольцо промежуточных буферов ~0.4 ГБ, крупные промежуточные — до 1 ГБ в пике. Сделано: загрузки от 16 МБ идут прямо в отображённую память копий буферов (`BufferCache::UploadDirect`, `SPARTAN_DIRECT_UPLOAD=0` — как раньше) — пиков в сотни МБ больше нет; мелкие загрузки остаются в кольце (прямая запись всех загрузок была на 2 FPS медленнее).
- **Проверено и отброшено:** ждать чтений при получении буфера только там, где буфер их читает, — игра **зависает** в бою (это ожидание ещё и публикует готовые чтения, которых игра ждёт в цикле); передача чтений на GPU вместо ожидания в загрузке — тоже зависание. Обе правки удалены.
- **Главный поток игры не считает, а ждёт.** 89% его времени — одна цепочка вызовов; внутри — цикл `pause` (`0xeba420`), пока состояние потока рендера игры (`0x4a40120`, с мьютексом и условной переменной) больше 1. Поток рендера сам занят процессором ~33%, остальное — ждёт события GPU. Значит, игра упирается не в процессор и не в мощность GPU, а в задержку цепочки «игра → сервис → GPU → сигнал готовности» на каждом кадре; синхронные ожидания в потоке GPU сервиса (чтения, скачивания) лежат прямо на этом пути. Следующий шаг — убирать их из пути кадра (асинхронные скачивания и чтения), а не ускорять отдельные части.
- **Падение 0x20040 найдено и исправлено (21.11.2026, 14e10977).** `Liverpool::ProcessCommands` ждал поток записи draw один раз — когда видел команды — и выполнял очередь до конца: команда, пришедшая после проверки (скачивание по сбою из потока кольца сервиса), шла параллельно с потоком B, и оба меняли `record_chunk`. Теперь ожидание перед каждой командой. Уровень: 6 прогонов без падения (было около одного на шесть).
- **Зависание в бою найдено и исправлено (d315d3fa).** Главный поток R&C каждый кадр крутится, пока последний тексель образа 480×200 R32F (`0x8106228500`) не перестанет быть -1.0 — результат GPU через чтение. Чтение публикует отложенная операция «по завершении копии», но в полёте могла быть только одна: копию, записанную, пока она ждала, никто не публиковал до следующего EOP или обращения, а игра стояла. Теперь операция на каждый тик копии. Бой: 8 из 8 прогонов (раньше зависал каждый 4–8-й, всегда в одном месте). Найдено сторожем `SPARTAN_HANG_DUMP=1` (регистры главного потока игры и адрес ожидания при тишине моста 3 с; сервис печатает, что знает об адресе).

- **Итог по бою (5 с, ~21 FPS в тяжёлой фазе).** Кадры ровные ~47 мс, а не редкие пики: «микролаги» — это темп ниже 30, который на 60 Гц показывается как 33/50 мс вперемешку. На кадр:
  - главный поток: ~30 мс ждёт поток рендера игры (цикл `pause`), ~9 мс — результат GPU, ~8 мс работает;
  - поток рендера: ~13 мс в коде игры, ~34 мс вне его, из них ~31 мс — один медленный сбой записи.
- **Этот сбой — ложное разделение страницы.** Поток рендера увеличивает счётчик структуры (`[r12+0x40]`, страница `0x81050bf000`, инструкция `0x17b30a6`; рядом `+0x48` — метка EOP), а шейдер каждый кадр пишет 16 байт той же страницы (`0x81050bf960`, texel-буфер). Кеш буферов следит страницами по 4 КБ: перед записью он скачивает данные GPU и ждёт задание, которое их пишет — весь кадр GPU, ~25 мс, а поток команд сервиса всё это время стоит.

Без скачивания (`SPARTAN_WRITE_NO_DOWNLOAD=1`) сбои — 2.7 мс на кадр, но кадр тот же: ожидание переезжает в поток записи отрисовок (`ResolveReadbacks`, ~30 мс раз в кадр — отложенное чтение образа, который GPU затем читает как буфер).
- **Вывод.** Процессор и GPU работают по очереди, а не внахлёст: каждый кадр игра где-то ждёт окончания текущей работы GPU. Чтобы получить 30, нужно убрать оба ожидания вместе: (1) запись процессора на страницу с данными GPU — не ждать, оставить байты GPU за ним и забрать их по готовности, не затирая при загрузке; (2) образ, читаемый как буфер, — копировать на стороне GPU, без круга через память игры. Попытки (2) раньше вешали игру, но тогда ещё была ошибка с потерянной публикацией чтения (исправлена в d315d3fa) — стоит повторить.

  - *Отложенная публикация при записи* (запись процессора на страницу с байтами GPU в полёте не ждёт; байты GPU пропускаются при загрузке и попадают в память игры по готовности). Причина: метку EOP сервис пишет, когда *записывает* команды, а не когда GPU их выполнил, — корректность держится на защите страницы с данными GPU: игра видит метку, читает данные, получает сбой и ждёт. Сняв защиту, правка отдала игре старые 16 байт (вероятно, результат отсечения), и игра рисовала лишнее. Неверные данные — недопустимо.

- **Что из этого следует.** Ожидание при сбое — не лишнее: игра действительно читает эти байты после метки. Укоротить можно только путь «команды игры → запись → отправка в Metal → готовность», или писать метки EOP по готовности GPU (тогда игра ждёт метку, а не сбой). Возможный обход ложного разделения — эмулировать запись процессора в счётчик (`isa_emulate`), не снимая защиту страницы: чтение данных GPU по-прежнему ждёт, запись — нет.
- Зависание на старте до первой отправки работы GPU — давнее (было 20.11 и до замеров), в последних прогонах ~1 из 5; не связано с правками.

Общее решение — метки по готовности GPU или автоматическое распознавание таких участков — впереди.

**Точные барьеры в KosmicKrisp (20.11.2026): проверено, выигрыша нет.**
- **Что сделано** (`KK_PRECISE_BARRIERS=1`, патч `packaging/macos/kosmickrisp-ps4mac-diagnostics.patch`):
  - кодировщик заканчивается без барьера-производителя;
  - следующий ждёт работу очереди (`barrierAfterQueueStages`), только если с тех пор был барьер Vulkan, событие, запрос, копия/заливка или начало командного буфера;
  - проход рендера всегда ждёт фрагменты предыдущей работы.
- **Результат.** Картинка верная, игра не зависает. Но FPS тот же (13,6–13,7 против 12,6–13,9 без режима — в пределах разброса прогонов).
- **Почему:** `KK_BARRIER_STATS=1` — 97% кодировщиков проходов и 74% compute и так начинаются после барьера Vulkan от видеоядра (смены раскладок при пинг-понге целей). Зависимости настоящие, работа на GPU последовательна по смыслу.
- **Вывод.** Режим оставлен выключенным. Время GPU (~34 мс compute + ~29 мс фрагментов на кадр) — исполнение самих шейдеров. GPU PS4 делает тот же кадр быстрее 33 мс; следующая цель — эффективность переведённых шейдеров (GCN → SPIR-V → NIR → MSL), начиная с самого тяжёлого (`cs 3370d82d`).
- **Замечание о замерах.** Разброс между одинаковыми прогонами достигает ±0,6 FPS (нагрузка на машину, своп); сравнивать стоит по нескольким прогонам.

**Шейдеры, первый шаг (20.11.2026): проверки границ буферов — ~15% кадра.**
- **Откуда проверки.** Видеоядро включает `robustBufferAccess`, `robustImageAccess` и их версии 2: перевод shadPS4 сам границ не проверяет, а семантику GCN «чтение за границей — 0, запись отбрасывается» отдаёт драйверу. KosmicKrisp оборачивает проверкой каждый доступ.
- **Замер** (`SPARTAN_NO_ROBUSTNESS=buffer|image|all`, R&C, режим сервиса):
  - без проверок для буферов — уровень 13,9 → **16,3 FPS**, драка 12,7 → **14,3**; кадры уровня и драки верные;
  - без проверок для изображений — выигрыша нет (12,9);
  - без обеих — игра зависает на старте.
- **Первое решение для R&C** — `SPARTAN_NO_ROBUSTNESS=buffer` без своих проверок (риск записи за границей); заменено вариантом ниже.
- **Безопасный вариант** (`SPARTAN_SHADER_BOUNDS`, перевод проверяет границы сам по `OpArrayLength`; Sirit получил `OpArrayLength`):
  - `=1` — все доступы: чтение с зажатым индексом и нулём за границей, запись под ветвлением, атомик под ветвлением с phi. Стоит столько же, сколько проверки драйвера: 13,8 FPS. Дорога сама проверка на каждом чтении, а не реализация в KosmicKrisp.
  - `=writes` — только записи и атомики. Уровень **15,8 FPS**, драка **14,7**, кадры верные. Порча чужой памяти исключена; чтение за границей вернёт соседние данные вместо нуля.
- **Падение сервиса.** Один раз за ~8 прогонов сервис упал (SIGSEGV по адресу 0x20040) на титуле. Вероятная причина — диагностика шага 3.6: на каждом сбое записи поток кольца читал состояние страниц кеша буферов (`IsRegionGpuModified`) без его блокировок. Теперь она только при `PS4MAC_FAULT_STATS=1`, а обработчик фатального сигнала сервиса печатает стек. После правки 4 из 4 прогонов без падений; что дело было именно в этом, не доказано.
- **Первый запуск после пересборки** медленнее (~14,5–14,9 FPS против 15,7–15,8): Metal заново собирает конвейеры.
- **В профиле R&C теперь** `SPARTAN_NO_ROBUSTNESS=buffer` + `SPARTAN_SHADER_BOUNDS=writes`. Если где-то появится мусор — `=1` (всё проверяется, на ~13% медленнее). Кеш шейдеров для каждого режима свой.

**Шейдеры, второй шаг (21.11.2026): тяжёлый compute `3370d82d` изнутри.**
- **Как достать шейдер:**
  - `SPARTAN_DUMP_SHADERS=1` с отдельной пустой папкой видеоядра (`SPARTAN_GPU_USER_DIR=<папка>`: кеш пуст, всё компилируется) выгружает GCN (`.bin`), IR и SPIR-V;
  - `MESA_KK_DEBUG=msl` печатает MSL всех шейдеров, а видеоядро при выгрузке ставит перед каждым compute-конвейером строку `Pipeline compile mark: cs_0x...` — по ней MSL находится в логе.
- **Размеры:** GCN 8 КБ → SPIR-V ~4 тыс. инструкций → MSL 16,5 тыс. строк (SSA с объявлениями, компилятору Metal это не мешает).
- **Что проверено:**
  - `NoContraction` стоит на 1 101 операции (сложения, умножения, FMA, деления: перевод сохраняет точное округление GCN). KosmicKrisp делает из него `#pragma METAL fp math_mode(safe)` на каждой операции, а сравнения — `safe` всегда (обходной манёвр 14). Опыт без `NoContraction` (режим `relaxed` почти везде) — FPS тот же (15,7). Режим математики Metal — не узкое место.
  - Проверок «дескриптор не нулевой» вокруг чтений текстур (`nullDescriptor`) в этом шейдере 12 — мелочь.
- **Вероятное объяснение оставшегося времени GPU — пропускная способность памяти:** M1 ~68 ГБ/с против ~176 ГБ/с у PS4, а R&C на 1080p рисует в G-буфер из нескольких целей. Проверить можно двумя способами:
  - захват кадра Metal (`MESA_KK_GPU_CAPTURE_DIRECTORY`) с разбором в Xcode — счётчики пропускной способности и стоимость шейдеров по строкам;
  - опыт с меньшим внутренним разрешением (для R&C нужен патч разрешения игры).

**Захват кадра Metal (21.11.2026, R&C, уровень).**
- **Что в захвате:** ~1 кадр — 166 кодировщиков рендера, 40 compute, 774 отрисовки, 192 dispatch. Xcode → Insights → Bandwidth: цели рендера 1080p (B10G11R11, A2B10G10R10 и др.) не сжимаются без потерь, потому что у них флаги `ShaderWrite` и `PixelFormatView`. Видеоядро shadPS4 ставит `STORAGE` и `MUTABLE_FORMAT` всем изображениям заранее.
- **Опыт `SPARTAN_LEAN_IMAGES=1`:** цветные изображения создаются без этих флагов и получают их (новый backing с копией, `Runtime::UpgradeBacking`) при первом представлении для записи из шейдера или в другом формате.
  - Без повышения игра даёт чёрный экран — представления в другом формате нужны.
  - С повышением картинка верная, повышение получают 44 изображения, среди них пять целей 1080p, в которые игра пишет из compute.
  - **FPS ниже**: попарно 16,3 и 16,4 без режима против 14,9 и 15,4 с ним.
  - Режим оставлен выключенным: самые нагруженные цели всё равно без сжатия, а сжатие и копии стоят своего.
- **Захват** — `tools/gpu_trace/capture_rnc_level.sh`; кадр уровня весит ~7,7 ГБ.

**Счётчики и вытеснение регистров (21.11.2026).**
- **Профилирование захвата в Xcode** (Performance) на 7,7-гигабайтном кадре не закончилось за 30 минут — на 8 ГБ памяти это не работает.
- **Через `xctrace`** набор счётчиков GPU не задаётся (инструмент Metal GPU Counters пишет пустые таблицы); нужен интерфейс Instruments.
- **Вытеснение регистров.** Та же трасса показывает **~430 событий в секунду** (`graphics-compiler-spill-events`, по 64–128 байт на поток): шейдеры после перевода не помещаются в регистры GPU и выгружают переменные в память.
  - Большая часть — в проходах рендера (их кодировщики пока без подписей); из подписанных — compute `6b7eaac0`, `a8dd8d63`, `3370d82d`.
  - Вероятный вклад перевода: обращения к буферам идут через 64-битные адреса (`ulong`-арифметика в MSL), что удваивает регистры на каждый адрес.
- **Разбор по подписям** (`tools/gpu_trace/spills_by_label.py`):
  - **стадия вершин** в проходах рендера — 320–496 байт на поток, больше всего событий; но вершины занимают ~2% времени GPU;
  - **compute** — 64–128 байт (`3370d82d` 128 байт, `6b7eaac0` 96–112).
- **`maxTotalThreadsPerThreadgroup`** KosmicKrisp уже задаёт по реальному размеру группы (64), так что вытеснение — свойство самого переведённого кода. Главный подозреваемый — 64-битная адресация буферов в MSL (~900 строк с `ulong` в одном шейдере).
- **Ограничители GPU на M1 недоступны:** в Instruments (Metal Application → Counter Set) есть только «Performance Limiters», и запись с ним выдаёт «Selected counter profile is not supported on target device»; профилирование захвата в Xcode на 8 ГБ не завершается. Узнать, во что упирается compute, можно только косвенно (опытами).
- **Снизить давление** = другая адресация буферов в компиляторе KosmicKrisp (база + 32-битное смещение). Это проект на несколько дней, выигрыш неизвестен. Сначала стоит узнать ограничители (Instruments, набор Limiters): если compute упирается не в ALU или регистры, вытеснение не главное.
  - **Проба на одном шейдере (24.11.2026): 32-битные смещения не ускоряют.** MSL шейдера `3370d82d` (`b44051201dceb8a4`, 16 тыс. строк, 4,8 тыс. с `ulong`) выгружен и подменён правленым через хук KosmicKrisp `KK_MSL_DUMP_DIR` / `KK_MSL_OVERRIDE_DIR` (патч `RnC/autotest/tools_msl/kk-msl-dump-override.patch`, не в проекте); скрипт `RnC/autotest/tools_msl/addr32.py` переписал 1 280 обращений «64-битная база + смещение» на указатель + 32-битное смещение. Трасса Metal на 720p (`trace_at.sh`, по 2–3 записи): без правки 4,37 / 4,31 мс на кадр, с правкой 4,22 / 4,48 / 4,49 — разница в шуме. Компилятор Metal сам сводит такую адресацию; переделка адресации в KosmicKrisp отброшена.
  - **Трасса Novalis в 720p (24.11.2026, `RnC/autotest/trace_nov.sh`, окно 1 с — 3 с на Novalis не успевали сохраниться за 5 мин).** Стоя у ламп 21,3 FPS, на ходьбе 23,2; GPU занят 73 / 72%. Подписанное: фрагменты 7,1 / 5,7 мс на кадр, compute 8,3 / 8,0, из них самый тяжёлый — `a2affd91` (20×12 групп) 3,0 / 2,8 мс (на первом уровне 0,2 мс: растёт со сценой, вероятно со светом), `6b7eaac0` 1,9 / 1,5; `3370d82d` на Novalis почти не виден. Подписана только около половины времени GPU. Одного главного тяжеловеса нет: даже двукратное ускорение `a2affd91` — около 3% кадра.
- **Опыт с разрешением (21.11.2026).** Внутреннее разрешение R&C — всегда 1920×1080 (у игры нет патча разрешения; настройка `render_resolution` меняет только окно). Готовое масштабирование сцены (`SceneTargets`) привязано к сцене God of War (триггер апскейлера по шейдеру) и для R&C не включается. Поэтому замер — диагностикой `SPARTAN_DIAG_RASTER_FRACTION=f`: каждый draw рисует только верхний левый угол f×f своего scissor. Фрагментная работа уменьшается в f² раз; вершины, compute и загрузка/сохранение вложений проходов остаются.
  - Уровень (`level5.txt`, сервис): f=1 — **16.4 FPS** (61 мс); f=0.7 (половина пикселей) — **20.3** (49 мс); f=0.5 (четверть пикселей) — **24.3** (41 мс).
  - Линейная модель: ~**35 мс** кадра не зависят от числа растеризуемых пикселей, ~**26 мс** пропорциональны им — почти всё фрагментное время GPU (~29 мс). Значит, фрагментная часть упирается в пиксели (заливка/полоса/шейдинг на пиксель), а не в вершины.
  - Вывод: более низкое внутреннее разрешение дало бы много. Только по фрагментам 720p (0.44 пикселей) даёт оценку **≥ 21–22 FPS**; больше, если compute-проходы игры (освещение, постобработка) тоже масштабируются с разрешением. Следующий шаг — патч разрешения R&C в профиле (найти размеры целей рендера в eboot), а не переделка адресации в KosmicKrisp.
- **Патч разрешения R&C (21.11.2026).** Размер сцены игра берёт из своих настроек рендера, которые начинаются со значений по умолчанию: функция по смещению `0x177ca90` пишет 1920 и 1080 двумя `mov dword`. Свой вывод 1920×1080 игра сохраняет и растягивает картинку до него сама. Патчи `Resolution Patch - 480p/720p/900p` в `games/CUSA01047/patches.xml` меняют эти два числа; `run.py` выбирает патч по `render_resolution` из `spartanport.ini`, как в God of War III.
  - Уровень (сервис): 1080p — 16.4 FPS, 900p — 20.1, 720p — **30** (потолок игры). Бой: 15.0, 18.8, ~23 (первые девять отчётов боя).
  - Предсказание опыта с обрезкой (≥ 21–22 FPS в 720p) перевыполнено: вычислительные проходы игры тоже масштабируются с разрешением.

**Совместимость на время перехода:** однопроцессная сборка остаётся рабочей (переключатель `PS4MAC_SINGLE_PROCESS`), пока двухпроцессная не догонит её по стабильности. Так каждую игру можно сравнить в обоих режимах.

**Главные риски шага:** задержка сбоев через мост (3.0 и 3.4), разделение `videoout/driver.cpp` (в нём смешаны состояние порта, поток показа и подготовка кадра), синхронизация прерываний с equeue.

## 8. Решения (20.11.2026)

1. **Репозитории:** ядро `ps4mac_port` с папкой `games/` (профили, патчи, записи для автотеста) + отдельные публичные **витрины игр** (RnCPort и следующие): README, логотип, ссылка на ядро и профиль.
2. **Имя платформы:** `ps4mac_port`.
3. **SpartanPort — гибрид:** отдельный репозиторий со своей структурой; исправления SpartanPort и shadPS4 забираем выборочно (cherry-pick, в основном видеоядро), свои общие исправления предлагаем им, когда подходят. Лицензия GPL-2.0.
4. **Формат профиля:** TOML.
5. **Функции God of War III** (предложение, ждёт подтверждения): GoW III остаётся в SpartanPort. Из его функций в платформу:
   - **оверлей настроек** — универсальный: общие пункты от ядра + пункты из профиля игры;
   - **масштабирование** — универсальное пространственное (MetalFX Spatial / FSR1) при показе кадра, внутреннее разрешение — патчем из профиля; временной апскейлер (камера, векторы движения) — модуль конкретной игры, если понадобится;
   - **хуки модов** (сферы, QTE, урон, читы) — не переносим: моды в общем виде = байтовые патчи профиля.
6. **Минимальная версия macOS:** 26 (Metal 4 в KosmicKrisp, ожидания между процессами).

## 9. Риски

- **Rosetta в macOS 28** (главный риск): macOS 27 предупреждает, что приложения для Intel, которым нужна Rosetta, в macOS 28 не откроются. Код игры у нас — x86-процесс под Rosetta. Apple обещала оставить часть Rosetta для старых игр; подойдёт ли она нашему рантайму, проверить на бете macOS 28. Если нет — свой перевод x86 → arm64 для CPU-части (графика уже нативная).
- **Сбои записи через мост**: задержка может съесть выигрыш нативности, если сбоев много → пакетирование, окна, битовая карта в общей памяти.
- **Одинаковые адреса в arm64-процессе**: области, занятые системой или библиотеками arm64-процесса, могут пересечься с адресами игры → резервировать область заранее при старте сервиса.
- **Отладка двух процессов**: журналы и трассы с общей временной шкалой (уже есть `SPARTAN_TRACE`, нужно расширить на оба процесса).
- **Совместимость с исправлениями shadPS4/SpartanPort**: изменения в видеоядре держать минимальными и изолированными.
